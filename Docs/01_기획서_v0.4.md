## 1. 설계 원칙

### 1-1. 네 가지 원칙

1. **손을 놓아도 돌아간다** — 필수 입력은 ① 찌 놓기 하나뿐. 탭은 있어도 되고 없어도 되는 효율.
   *멍하니 보고만 있어도 물고기가 잡히는 상태가 이 게임의 기본값이다.*
2. **유일한 실력은 예측** — 궤도는 반드시 규칙적·주기적. 랜덤 워크를 넣는 순간 재미가 0이 된다.
3. **보는 것 자체가 재밌어야 한다** — 조작이 없는 시간이 대부분이므로, 물결·유영·입질 연출이
   그 자체로 기분 좋아야 한다. 이 방향에서는 **연출 폴리싱이 시스템만큼 중요하다.**
4. **습성은 한 문장으로 학습된다** — "오징어는 제자리에 있다가 갑자기 튄다" 수준.

### 1-2. 핵심 장치 ① — 찌를 옮기면 비용이 발생한다

> **찌를 다른 곳에 놓는다 = 새 착수 = 주변 놀람 + 관심 큐 전부 리셋**

**이 규칙이 없으면 어떻게 되는가**

```
참치이 8자 궤도를 돌고 있다 → 손가락으로 찌를 참치 위에 갖다 댄다 → 문다 → 반복
```

궤도 모양도, 습성 6스탯도, 어종 구분도 전부 무의미해지고 게임은 "물고기 탭하기"가 된다.

**이 규칙이 있으면**

```
참치 위에 갖다 대면 → 놀라서 물러난다 → 실패
→ 참치이 "지나갈 자리"를 예측해서 미리 놓고 기다려야 한다
→ 8자 궤도를 눈으로 따라가고, 연어 레인을 비껴간 자리를 골라야 한다
```

원 기획의 *"궤도를 보고 미리 찌 움직이는 정도의 자유도"* 가 이 규칙 하나로 자동 강제된다.

**세부**

- 빈 찌 회수(0.3s) + 재착수(0.3s)로 최소 시간 비용이 자연 발생
- **연속 재착수 페널티**: 3초 내 반복 착수 시 놀람 반경·지속 ×1.5 (누적 상한 ×2.5).
  스팸 억제 + "같은 자리에 계속 던지면 물고기가 경계한다"는 명분
- **세션 타이머가 곧 리셋 통화** — 리셋할수록 남은 시간이 준다. 미끼 시스템 없이 비용이 붙는다

**찌 이동의 진짜 용도**: 지금 오는 연어를 떼어내려는 게 아니다(참치 관심도 같이 날아가서 대부분 손해). **"이 자리는 연어만 오는 자리였구나"를 깨달았을 때 옮기는 것** — 초기 배치 실수의 교정이다. 그래서 실력의 대부분은 **처음에 어디 놓느냐**에 있다.

### 1-3. 핵심 장치 ② — 잡는 것 자체가 비용이다

| 처리 | 점수 | 찌 상태 | 주변 방해 |
|---|---|---|---|
| **잡는다** (자동 또는 탭) | +점수 | 걷어올렸다 다시 던짐 | **큼** — 물장구, 참치 관심 전원 리셋 |
| **놓아준다** (선별 회수) | 0 | 그대로 유지 | **작음** — 참치 계속 접근 |
| **빈 찌 회수 후 이동** | 0 | 새 자리 | **큼** + 연속 재착수 페널티 |

직관적으로도 맞다 — 낚싯대를 걷어올리면 물이 크게 튀고, 물고기가 그냥 가면 조용하다.

> **"연어를 잡을수록 참치이 멀어진다."** 이 한 줄이 게임의 긴장이다.

**이게 자동 회수와 충돌하지 않는 이유**가 중요하다. 손을 안 대면 전부 자동으로 잡히고, 그러면 계속 물장구가 인다.
즉 **번잡한 자리는 저절로 "많이·작게", 조용한 자리는 저절로 "적게·크게"** 가 된다.
탭이 하던 양·질 트레이드오프가 **찌를 어디에 놓느냐로 옮겨간 것**이지 사라진 게 아니다.

### 1-4. 조작의 세 층위

| 층위 | 행동 | 필수인가 | 얻는 것 |
|---|---|---|---|
| 기본 | **찌 배치** | 필수 (1회) | 무엇이 잡히는지가 여기서 결정된다 |
| 선택 | **탭 = 즉시 회수** | 아니오 | 처리량↑ 대신 물장구↑ → **양을 늘리고 질을 낮춘다** |
| 해금 | **선별 회수** | 아니오 | 어종별 놓아주기 → 참치 획득 약 2배 |

**실측 (90초, 봇, 24세션)**

| | 마릿수 | 점수 | 폭 | 참치 |
|---|---|---|---|---|
| 완전 무입력 방치 | 10.9 | 40.9 | 8~93 | **0.8** |
| 자동 + 즉시 탭 | **12.9** | 40.5 | 18~88 | 0.6 |
| 선별 (연어·멸치 놓아줌) | 1.9 | 36.7 | 0~70 | **1.1** |

**세 방식의 기대 점수가 거의 같다.** 처음엔 탭이 이득이 되게 맞추려 했는데,
탭을 많이 할수록 물장구가 잦아져 참치이 줄기 때문에 자연히 상쇄된다.

이건 실패가 아니라 **지배 전략이 없는 상태**다. 셋 다 40점 근처인데 구성이 다르다 —
탭하면 많이 잡고, 손 놓으면 참치 확률이 높고, 선별하면 참치만 노린다.
**압박 없는 방치형에서는 "탭해야 이득"보다 이쪽이 낫다.** 아무도 의무감으로 화면을 두드리지 않는다.

## 2. 코어 루프

```
낚시터 선택 → 세션 시작(90초) → [ 착수 → 관찰 → 입질 → 자동 회수 → 집계 ] 반복 → 종료 → 결과
                                   └ 손을 놓아도 계속 돈다. 자리가 나쁘다 싶으면 옮긴다
```

### 2-1. 한 사이클

| # | 단계 | 플레이어 | 시스템 |
|---|---|---|---|
| 1 | 착수 | 수면 탭 | 찌 낙하 + 파문, 반경 내 `Startle` |
| 2 | 정착 | 대기 | 놀란 물고기 궤도 복귀, 찌 인지 상태 전환 |
| 3 | 관심 | 관찰 | 호기심 판정 통과 개체가 궤도 이탈 → 찌로 직진 **(복수 가능)** |
| 4 | 입질 | — | 가장 먼저 도달한 **1마리**가 히트 슬롯 점유. 찌 잠김 |
| 5 | 회수 | (탭은 선택) | 입질 시간 종료 → **자동 획득**(큰 소란). 탭하면 즉시.<br>선별 회수로 지정한 어종은 **놓아줌**(작은 소란) |
| 6 | 집계 | — | 우측 바구니 +1, 인벤토리·도감 갱신 |

### 2-2. 실제 플레이 — 첫 5초

```
0.0초  화면 왼쪽 아래에 찌를 던진다.
       근처 연어 2마리가 화들짝 물러난다.                    ← 놀람

0.5초  연어들이 원래 헤엄치던 길로 돌아간다.
       "저기 뭔가 떨어졌다"를 인지한 상태.                        ← 찌 인지

1.0초  연어A가 갑자기 방향을 틀어 찌 쪽으로 직진하기 시작.
       ★ 다른 물고기는 구불구불한데 이 놈만 직선으로 온다 → 눈에 띈다

2.0초  연어B도 같은 행동. 2마리가 찌로 오고 있다.

2.5초  오른쪽에서 8자를 그리던 참치이 방향을 틀어 접근 시작.
       아주 느리다. 도달까지 7초.
```

**2.5초 시점에 화면이 보여주는 것**

| 물고기 | 점수 | 찌까지 |
|---|---|---|
| 연어A | 1점 | **0.5초** |
| 연어B | 1점 | 1.5초 |
| **참치** | **30점** | **7초** |

이게 **관심 큐**다. UI도 아이콘도 아니고, **찌를 향해 줄 서서 오는 물고기들**이 화면에 그냥 보이는 것이다.

### 2-3. 유일한 의사결정 — 어디에 놓을 것인가

위 시나리오에서 플레이어는 손을 대지 않아도 된다. 연어A는 자동으로 잡히고, 그 물장구에 참치은 돌아간다.
**그 결과를 만든 것은 "찌를 저기에 놓은 선택"이다.**

- **연어 레인 위** → 계속 물린다 → 계속 물장구 → 참치은 영원히 안 온다. 많이·작게
- **참치의 8자 궤도 위, 연어가 뜸한 자리** → 입질이 드물다 → 물이 잔잔하다 → 참치이 들어온다. 적게·크게

**실측으로 확인된 것**: 완전 무입력 상태에서 찌 위치만 바꿔도 **점수가 20.6점 ~ 39.7점(1.9배)** 으로 갈린다.
마릿수는 어디 놓든 8.9~10마리로 거의 같은데 **무엇이 잡히는지가 완전히 달라진다** — 참치 획득이 0.1마리와 0.8마리로 8배 차이가 난다.

> 조준하고, 결과가 20초에 걸쳐 펼쳐지는 것을 지켜본다. **이게 코어다.**

### 2-4. 세션이 방치 톤을 해치지 않게

타이머는 압박 장치가 아니라 **"이 낚시터에 머무는 시간"** 프레이밍으로.

- 세션 종료는 **실패가 아니다** — 잡은 건 전부 가져간다. 페널티 없음
- 일시정지 지원
- 남은 시간 UI는 경고색·초읽기 연출 **금지**. 조용한 게이지로
- **후속 "낚시 시간 증가"가 여기 붙는다** — 세션 길이가 첫 번째 성장 축

## 3. 물고기 데이터

### 3-1. 습성 스탯

> **v0.4 — 스탯은 두 덩어리다.** 지금까지 전부 `FishSpeciesSO` 하나에 뭉쳐 있었는데,
> 어종 표를 보면 `laneAmp` · `loopA` · `hoverT` 칸의 **절반 이상이 빈칸**이다.
> 그건 "여기 타입 계층이 빠져 있다"는 신호다.
>
> | 어디에 속하나 | 무엇 |
> |---|---|
> | **운동 법칙(타입)** | 사행 폭·주기, 8자 반경·주기, 부유·대시 시간, 귀소 반경 |
> | **어종** | 경계심 · 호기심 · 접근속도 · 식탐 · 선회율 · 몸길이 · 파동 · 구역 |
> | **개체** | 무리/독립 (§4-4), 크기 편차, 접근 단계의 좌우 선택 |
>
> 어종은 **타입을 참조하고 그 파라미터만 채운다.** 어종이 늘어날 때 표가 안 무너진다.

어종 하나 = `FishSpeciesSO` 하나. 6개가 습성을, 1개(선회율)가 이동 물리를 담당한다.

| 스탯 | 의미 | 영향 |
|---|---|---|
| **PathType** | 유영 궤도 아키타입 | 예측 난이도 |
| **Zone** | 서식 구역 (화면상 위치 대역) | 찌를 어디에 놓을지 |
| **Wariness** 경계심 | 놀람 반경 / 지속시간 | 첫 접근까지의 딜레이 |
| **Curiosity** 호기심 | 관심 전환 확률 (1초 주기 판정) | 물릴 확률 그 자체 |
| **ApproachSpeed** | 관심 → 도달 시간 | 히트 슬롯 경쟁 순위 |
| **Greed** 식탐 | 입질 윈도우 길이 | 회수 조작 난이도 |
| **TurnRate** 선회율 | 초당 최대 회전 각도 (§5-3) | 접근 경로의 곡률, 몸집 체감 |

**파생값**: `NoticeRadius = 놀람 반경 × 1.9`
이 반경 안에 있을 때만 호기심 판정이 돈다. 경계심 높은 놈이 멀리서부터 찌를 인지한다 — 자연스럽고, 스탯을 7개로 늘리지 않아도 된다.

**`MinNoticeR` (경계심 높은 어종만)**: 이 거리보다 **가까우면 관심이 생기지 않는다.**
참치은 코앞에서 갑자기 마음을 바꾸지 않고 멀리서 알아채고 들어온다 — 그래야 접근에 시간이 걸리고, §1-3(연어를 잡을수록 참치이 멀어진다)이 실제로 성립한다. **이게 없으면 참치이 연어 잡는 틈에 그냥 통과한다.**

> **주의 — 호기심 확률은 '개체당 초당'이다.** 인지 반경 안에 5마리가 있으면 실효 발동률이 5배가 된다.
> 스펙 수치를 정할 때 반드시 동시 개체 수와 인지 반경을 함께 봐야 한다.

### 3-2. 희귀도 축 하나로 전부 갈린다

- **연어**: 경계심↓ 호기심↑ 접근↑ 식탐↑ → 아무것도 안 해도 잡힌다 (방치 보상)
- **참치**: 경계심↑ 호기심↓ 접근↓ 식탐↓ → 오래 기다리고 정확히 탭 (실력 보상)

별도 난이도 로직 불필요. 스탯 밸런싱만으로 난이도가 나온다.

### 3-3. 사이즈(cm) — 필드만, MVP 미표시

- 스폰 시 어종별 `minCm ~ maxCm`에서 결정 (정규분포 — 큰 개체가 희소하게)
- MVP UI 미표시. 데이터만 굴리고 저장
- 스프라이트 스케일에 **±10%만** 반영 → 수치 없이도 화면이 단조롭지 않음
- 완전 구현(스케일 크게 + 궤도 느리게 + 경계심 높게)은 후속

**지금 필드를 넣는 이유**: 후속 납품이 규격을 요구할 가능성이 높고, 도감의 "최대 기록"이 어종 4종만으로도 반복 플레이 이유를 만든다. 나중에 넣으면 세이브 마이그레이션 + 점수 밸런싱 전면 재작업.

## 4. 유영 궤도

> 스플라인 에셋 만들지 말 것. **파라메트릭 함수 + 시드**로 충분하고, 순수 함수라 결정론적이며 테스트가 쉽다.
> 좌표계: 수면 영역 **16 × 9 유닛** 기준 (실제 해상도에 맞춰 스케일)

### 4-1. 운동 법칙 3 + 변형자 1

> **v0.4 정정.** v0.3 은 "아키타입 4종"이라고 적었지만 넷은 같은 종류가 아니다.
> **School 은 법칙이 아니라 Lane 위에 얹은 변형자**다. 벤치에서 가상 어종 3종을 넣어 확인했다.

**운동 법칙 (PathType)**

| 법칙 | 수식 | 예측성 | 플레이어가 배우는 것 |
|---|---|---|---|
| **Lane** 회유 | `p = start + dir·vt + perp·A·sin(ωt)` | ★★★ | "저 라인 위에 놓으면 온다" |
| **Loop** 순회 | `p = c + (a·cos ωt, b·sin 2ωt)` 8자 | ★★☆ | "8초 뒤 여기로 돌아온다" |
| **Hover-Dash** | 부유 → 짧은 대시(ease-out) → 정지 반복 | ★☆☆ | "예측 안 되지만 안 멀리 간다" |

**변형자 (Modifier)**

| 변형자 | 효과 | 어느 법칙 위에도 얹힌다 |
|---|---|---|
| **School** 무리 | 리더 1 + 추종자 n. 추종자는 리더의 **머리 방향** 기준 고정 오프셋 + 미세 노이즈 | ○ |

> Lane 무리(멸치)와 Hover-Dash 무리(피라미) 둘 다 성립하는 것을 실측으로 확인했다.
> 추종자가 리더의 **속도 벡터**를 쓰면 안 된다 — Hover 리더는 떠 있는 동안 속도가 0이라
> 대형이 각도 0으로 스냅한다. 이게 무리를 Lane 밖으로 못 내보내던 원인이었다.

**공통 인터페이스** — 새 법칙은 이 네 개만 구현하면 된다.

```
init(f, P, band)        경로 상태 초기화
pos(f, t, P)      →     t 시점의 위치
anchor(f, P)            경로를 현재 위치에 다시 앵커 (복귀용)
tick(f, dt, P, sp)      선택 — 스스로 조향하는 법칙만
플래그: wraps(화면 밖 랩) · steersItself
```

> ⚠️ **Hover-Dash 는 순수 함수가 아니다.** Lane·Loop 는 `p = f(t)` 지만
> Hover-Dash 는 위치를 매 프레임 적분하는 **시뮬레이션 에이전트**다. 시점 t만으로 위치를 못 구한다.
> §9 의 "궤도 계산은 순수 함수 → 결정론 = 리플레이·시뮬레이션 공짜"는
> **Hover-Dash 에 대해서는 성립하지 않는다.** 리플레이를 붙일 때 이 어종만 별도 처리가 필요하다.
> (`PathEvaluator.cs` 에 hover 가 없는 것도 같은 이유다 — 코드는 이미 갈라져 있었고 문서만 안 갈라져 있었다.)

**타입 계층 검증 조건**: 어종이 8종이 됐을 때 **각 법칙에 2종 이상**이 들어가는가.
안 들어가면 그 법칙은 타입이 아니라 그 어종의 이름일 뿐이다.

### 4-2. 절대 규칙

- **모든 궤도는 주기적이다.** 화면 밖 이탈 시 반대편 재진입(Lane) 또는 순환(Loop).
  "기다리면 돌아온다"가 성립해야 예측 플레이가 산다
- **주기는 관찰 가능한 길이로.** Loop 주기 8~12초. 3초면 못 읽고 30초면 지루하다
- 비예측 어종(Hover-Dash)은 **이동 반경을 좁게** 잡아 보상한다

**사행 주기 (v0.4 변경): 연어 4.0 → 8.0초, 멸치 3.4 → 6.8초**

폭(A)은 그대로 두고 주기(T)만 2배로 늘린다. 이유는 머리 흔들림이다 —
사행 궤도는 **진행 방향 자체가 ±38° 흔들리고**, 머리가 그걸 따라가면 순항 중에도
3초에 76°씩 도리도리한다. 주기를 2배로 하면 그 흔들림이 ±21° 로 반감된다.

폭을 줄이는 것과 달리 **게임이 바뀌지 않는다**:

| | 좌우 폭 | 화면 가로지르는 시간 | 가로지르며 흔드는 횟수 |
|---|---|---|---|
| v0.3 (T=4) | 0.6 | 13초 | 3.3회 |
| v0.4 (T=8) | **0.6 그대로** | **13초 그대로** | 1.7회 |

물고기가 지나는 띠도, 몇 초마다 오는지도 안 바뀐다. 그 안에서 지그재그를 덜 칠 뿐이고,
§4-1 의 *"저 라인 위에 놓으면 온다"* 는 선이 더 곧아져서 **오히려 읽기 쉬워진다**.

> 대안이었던 '머리 감쇠'(머리가 진행 방향을 일부만 따라가게 함)는 **채택하지 않았다.**
> 흔들림은 줄지만 머리가 진행 방향에서 벌어지는 **게걸음**이 생긴다. 실측 비교:
> 머리 감쇠는 연어 흔들림 40°·슬립 15°, 주기 2배는 **21°·8°** 로 두 지표 모두 낫다.

### 4-3. 구역(Zone)

> v0.2의 "수심대(DepthBand)"를 대체. 탑다운에서 화면 세로축은 깊이가 아니라 거리이므로 명칭과 개념을 수정.

수면을 세로 3밴드로 나눈다 — **상단 / 중앙 / 하단**. 어종별 선호 밴드 + 이탈 허용치.

**연출 규칙**: 상단 = 얕은 쪽 / 하단 = 깊은 쪽으로 통일한다. 그림자 오프셋(§6-4)으로 표현하면 "깊은 곳의 참치"이 시각적으로 읽힌다.

→ "귀한 놈은 아래쪽 깊은 데 사는데 거기 연어 무리도 산다" 같은 **공간 퍼즐**이 생긴다.

### 4-4. 무리는 개체의 성질이다 (v0.4 신설)

"멸치는 무리 어종"이 아니라 **"멸치는 대체로 무리를 짓는다"** 가 맞다.
같은 어종 안에서 갈려야 화면이 산다.

| 어종 | 무리 | 독립 | 무리 크기 |
|---|---|---|---|
| 멸치 | 85% | 15% | 5~8 |
| 노란 피라미 | 80% | 20% | 6~9 |
| 연어 | 30% | 70% | 2~3 |
| 은빛 학공치 | 45% | 55% | 2~4 |

`school = { n, r, solo }` 를 어종에 두고 **스폰 시 개체마다 굴린다.**
연어가 가끔 둘셋씩 몰려다니는 편이 전부 흩어져 있는 것보다 살아 보인다.

> 구현 주의: 추종자는 리더를 **종 이름으로 찾으면 안 된다.**
> 무리 어종이 둘이 되는 순간 피라미가 멸치 리더를 따라간다. 개체를 직접 참조할 것.

## 5. 상태 머신

```
Roam            궤도 추종 (기본)
 │  ← 착수 이벤트 (놀람 반경 내)
 ▼
Startle         찌 반대 방향으로 물러남
 ▼
Wary            궤도 복귀. NoticeRadius 안이면 1초 주기 호기심 판정
 │  ← 판정 성공
 ▼
Notice   0.30s  ★ 발견 동작 — 궤도를 멈추고, 살짝 뒤로 움찔한 뒤,
                머리를 찌 쪽으로 홱 돌린다. 꼬리 비트는 거의 정지
 ▼
Interested      궤도 이탈, 찌로 직진 접근          ★ 복수 마리 동시 가능
 │  ← 도착. 히트 슬롯이 차 있으면 → 흥미 상실, Roam 복귀 (쿨다운 3s)
 ▼
Bite            히트 슬롯 점유 (동시 1마리). 찌 잠김, 입질 시간 시작
 ├─ 탭          → Caught  (즉시 획득. 입질 시간을 건너뛴다)
 ├─ 시간 만료     → Caught  (자동 획득 — 기본 동작)
 └─ 시간 만료     → Release (선별 회수로 지정한 어종만. 조용히 이탈, 찌는 유지)

  Caught  → 찌 걷어올림 → 재착수 = 큰 소란 (주변 관심 전원 리셋)
  Release → 작은 소란 (반경·지속 절반). 찌는 그 자리 유지
```

### 5-0. 착수는 '유인 이벤트'다 — 전부 도망가면 안 된다 ★

**찌 배치는 이 게임의 유일한 필수 조작이다. 그 조작에 대한 응답이 "전부 도망"이면 안 된다.**
행동의 첫 피드백이 거절이고, 그다음 몇 초는 아무 일도 안 일어난다. 보는 게임에서 최악의 첫 박자다.

그렇다고 단순히 뒤집으면 §1-2가 무너진다 — 찌를 참치 위에 갖다 대는 게 오히려 이득이 되어버린다.
**거리로 나누면 둘 다 성립한다.** 실제 물리와도 맞다: 코앞의 물장구는 놀라게 하고, 멀리서 들리는 물장구는 궁금하게 한다.

| 찌로부터의 거리 | 반응 |
|---|---|
| `< 놀람 반경` | **Startle** — 화들짝 물러난다. §1-2 유지 |
| `놀람 반경 ~ 인지 반경` | **즉시 관심 판정** (어종별 유인 확률) — 방향을 틀어 다가온다 |
| `> 인지 반경` | 반응 없음 |

**어종별 유인 확률**

| 어종 | 유인 확률 | 의미 |
|---|---|---|
| 연어 | 45% | 물장구에 잘 몰린다 |
| 멸치 | 38% | 무리째 반응 |
| 오징어 | 30% | 굼뜨게 반응 |
| **참치** | **0%** | **물장구에 오지 않는다** |

참치만 0인 게 핵심이다. 덕분에 플레이어가 배울 문장이 하나로 정리된다:

> **작은 놈은 물장구에 몰리고, 참치은 조용해져야 온다.**

이건 §1-3(잡을수록 참치이 멀어진다)을 약화시키는 게 아니라 **강화한다.**

**두 가지 보정**

- **최소 1마리 보장** — 확률만 굴리면 아무 반응 없는 착수가 생기고, 그건 '먹통'으로 읽힌다.
  한 마리도 안 걸리면 가장 가까운 개체를 끌어온다. *조작에 대한 응답은 확률이면 안 된다.*
- **유인 피로도** — 직전 착수로부터 2.5초 안이면 유인 확률이 55%까지 떨어진다.
  이게 없으면 "빨리 잡을수록 유인이 더 자주 발동"하는 복리가 생겨 탭이 사실상 의무가 된다.
  명분도 자연스럽다 — 같은 자리에 계속 던지면 물고기가 시큰둥해진다.

### 5-1. Notice — 발견하는 순간이 보여야 한다 ★

관심 전환이 즉시 일어나면 **"발견"이라는 사건이 화면에 없다.** 그냥 어느 순간 방향이 바뀌어 있을 뿐이라 플레이어가 못 읽는다.

0.30초짜리 상태를 하나 끼운다.

| 구간 | 동작 |
|---|---|
| 이동 | 궤도 추종 중단. **거의 정지** + 아주 살짝 뒤로 움찔 |
| 회전 | 머리를 찌 쪽으로 **빠르게** 돌린다 (일반 회전 스무딩의 2배 속도) |
| 파동 | 꼬리 비트 거의 정지 (진폭 ×0.3, 주파수 ×0.22) |

주변이 전부 꼬물거리는데 **한 마리만 얼어붙었다가 방향을 트는 것**이 발견 신호다. 아이콘 없이 동작만으로 읽히고, 애니메이션의 anticipation 원칙 그대로다.

### 5-2. 도착했는데 자리가 차 있으면 — 떠난다

**대기시키지 않는다.** 프로토타입에서 두 가지 방식을 다 시도했고 둘 다 틀렸다.

- 찌 주변 선회 → 누가 뭘 하는 중인지 알 수 없는 난장판
- 줄 세우기 → 무리(멸치 5~8마리)가 통째로 도착하면 화면 절반이 정지한 물고기로 찬다

그리고 더 근본적으로, **대기열은 플레이어의 결정에 아무것도 보태지 않는다.** 판단에 필요한 정보는 *아직 오고 있는* 물고기지, 이미 도착해 멈춰 선 물고기가 아니다.

> **도착 → 자리 있으면 문다 / 차 있으면 흥미를 잃고 궤도로 복귀 (재관심 쿨다운 3초)**

자연스럽고(먹을 게 없으니 간다), 물이 계속 움직이고, 버그 표면이 통째로 사라진다.

### 5-3. 이동 모델 — 선회율 제한 + 전진 전용 ★

**위치와 회전을 따로 굴리면 안 된다.** 목표 지점으로 위치를 직선 보간하면서 각도를 따로 보간하면,
속도가 0에 가까운 순간(발견 동작, 입질, 오징어 부유)에 **제자리에서 빙글 도는 그림**이 나온다.
몸이 향한 방향과 실제 가는 방향이 어긋나서 옆으로 미끄러지기도 한다.

물고기는 미사일과 같은 제약을 받는다 — **머리 방향으로만 나아가고, 초당 정해진 각도까지만 돈다.**

```
θ_목표 = atan2(대상 - 현재위치)
Δ      = wrapAngle(θ_목표 - θ)
θ     += clamp(Δ, -ω·dt, +ω·dt)      ← 선회율 제한
위치  += (cos θ, sin θ) · v · dt      ← 전진만
```

그 결과 접근 경로가 **직선이 아니라 호(arc)** 가 되고, 이게 곧 물고기다운 움직임이다.

**선회 반경 `R = v / ω`** 가 어종의 성격이 된다.

#### v0.4 — 식을 뒤집는다: ω = v / R

선회율(ω)을 **직접 주면 안 된다.** 그러면 느린 물고기일수록 반경이 작아져 제자리에서 돈다.
v0.3 의 `notice` 상태가 그랬다 — 선회율 440°/s 에 전진 0.25/s → **반경 0.033유닛,
몸길이의 3.5%.** 회전이지 선회가 아니었다.

**최소 선회 반경을 몸길이 배수로 정하고, 거기서 선회율을 뽑는다.**

```
ω_max = v / (R_min · L)          R_min ≈ 0.55 몸길이
ω     = min(ω_max, 어종 선회율 상한)
```

이러면 어떤 상태에서도, 어떤 속도에서도 호가 보장된다. 실측 최소 반경 **0.4 ~ 0.96 몸길이**.

**두 가지 보정이 반드시 함께 간다.**

| 보정 | 왜 | 없으면 |
|---|---|---|
| **근접 선회 보정** (§11 `CloseTurnBoost`) | 목표 코앞에서만 반경을 조인다 (배수 0.40) | 최소 반경이 도착 판정보다 크면 **영원히 맴돈다** |
| **속도 적합** (v0.4 신설) | 반경이 남은 거리보다 커지지 않게 **속도를 깎는다** — `v ≤ ω_max · d · 0.85` | 빠른 어종이 **소용돌이**를 돈다 |

> **소용돌이는 선회율 문제가 아니라 속도 문제다.** `R = v/ω` 이므로 빠를수록 크게 돈다.
> 연어 돌진 속도 4.75 · 상한 200°/s → 반경 **1.36유닛**, 도착 판정(0.35)의 4배.
> 선회율을 더 올리면 팽이가 되므로 **반대로 감속시킨다** — 실제로도 급선회하려면 속도를 줄인다.
> 실측: 학공치 도달 6/10 → **10/10**, 접근 3.7초 → **0.5초**.
>
> 안전망: 그래도 3.5초 이상 못 들어가면 **한 번 크게 빠졌다가 다시 온다.**
> 무한히 도는 것보다 "놓쳤네, 다시" 가 보기에도 낫다.

**머리 방향은 진행 방향과 같지 않아도 된다** — 다만 상한을 둔다.
사행 궤도에서 머리를 진행 방향에 100% 붙이면 순항 중에도 도리도리한다(§4-2).
머리가 진행 방향에서 벗어날 수 있는 각도(**슬립**)에 상한 14°를 둔다.
상한이 없으면 Loop 처럼 진짜로 빨리 도는 궤도에서 **게걸음**이 나온다.

| 어종 | 선회율 ω | 180° 도는 데 | 접근 시 선회 반경 |
|---|---|---|---|
| 멸치 | 280°/s | 0.64s | 0.61 |
| 연어 | 200°/s | 0.90s | 0.72 |
| 오징어 | 95°/s | 1.9s | 0.90 |
| **참치** | **85°/s** | **2.1s** | 0.34 |

참치의 무게감은 반경이 아니라 **각속도**에서 나온다 — 몸을 돌리는 데 2초가 걸리는 게 눈에 보인다.

**두 가지 안전장치**

- **근접 부스트**: 목표까지 1.6유닛 안으로 들어오면 ω를 최대 2.6배까지 올린다.
  먹이를 낚아채는 동작이면서, 선회 반경 때문에 목표를 영원히 맴도는 *미사일 문제*를 막는다
- **접근 타임아웃 20초**: 그래도 못 닿으면 흥미를 잃고 궤도로 복귀

**상태별 적용**

| 상태 | 방향 결정 | 이동 |
|---|---|---|
| Roam | 경로의 진행 방향 (선회율 ×2.5로 완만히 제한) | 경로가 위치를 결정 |
| Notice | 찌 방향, 선회율 **×3** | 접근 속도의 35%로 **미끄러지며 꺾는다** |
| Interested | 찌 방향 + 근접 부스트 | 머리 방향 전진 |
| Bite | **고정** — 문 순간의 각도 유지 | 정지. 좌우 ±11° 몸부림(회전 아님) |
| Hover-Dash | 부유 중 조준을 정하되, **트는 건 돌진하면서** | 부유 = 미세 활강, 돌진 = 제트 펄스 |

**마지막 줄을 v0.4 에서 뒤집었다.** 원래는 *"부유하는 동안 천천히 몸을 틀어두고 돌진은 이미
향한 쪽으로만"* 이었는데, 이게 바로 제자리 회전의 원인이었다.

> ⚠️ **부유 중에는 돌 수 없다 — 그게 물리적으로 옳다.** ω = v/R 이므로 속도가 0에
> 가까우면 어떤 반경으로도 못 돈다. 그런데 구현은 부유 속도 0.07 에 선회율 상한을
> 67°/s 로 줬다. **반경이 몸길이의 6%.** 컴퍼스 바늘이다.
> 실측: 선회 프레임 1706개 중 **1699개(99.6%)가 제자리 회전**이었다.

**고친 방식 — 방향 전환을 돌진 안으로 옮긴다.**

| 구간 | 속도 | 선회 |
|---|---|---|
| 부유 | 0.20 (미세 활강) | ω = v/R 그대로 → **최대 14°/s.** 게으르게 기울 뿐 |
| 돌진 | 제트 펄스 `12u(1-u)²`, 최대 ~9 | ω = v/R → 어종 상한(150°/s)까지 |

돌진이 **직선이 아니라 호**가 된다. 실측 호 크기 중앙값 34°, 최대 93°.
제자리 회전은 **0°** — 60초 동안 1364° 를 도는데 그중 제자리 회전 반경에서 도는 각도가 없다.

> 제트 펄스를 `3(1-u)²`(즉발 후 활강)에서 `12u(1-u)²`(차올랐다 터지고 활강)로 바꿨다.
> 둘 다 적분이 1 이라 이동거리는 같다. 전자는 첫 프레임 속도가 22(몸길이의 23배/초)로 튄다.
> **후자는 최고 속도가 호를 그리는 구간에 온다** — 그래서 선회가 눈에 보인다.

**핵심 규칙**

- `Interested`는 **다수**, `Bite`는 **1마리**
- 히트 슬롯은 **선착순** → §2-3의 의사결정이 여기서 발생
- **찌를 걷어올리면(잡았든 옮기든) 그 찌를 향하던 관심은 거리와 무관하게 전부 사라진다** ★
  놀람 반경 안만 리셋하면 §1-3이 성립하지 않는다 — 참치이 연어 잡는 틈에 그냥 통과한다
- `Escape`는 **반경 절반, 지속 절반**의 작은 놀람. 찌는 그 자리에 유지

### 5-4. 관심(Interested)과 입질(Bite)은 다른 종류의 신호다 ★

이 둘을 같은 원칙으로 다루면 안 된다.

| | 관심 | 입질 |
|---|---|---|
| 성격 | **주변 정보** — 여러 마리, 계속 변함 | **지금 일어나는 사건** — 1마리, 0.6~1.5초 |
| 아이콘 | **쓰지 않는다** — 3~4마리에 아이콘이 뜨면 난장판이고 톤을 깬다 | **명시 UI를 쓴다** |
| 전달 수단 | 동작(§5-1, §5-2) | 명시 UI + 동작 |

자동 회수로 바뀌면서 입질은 더 이상 *입력 요구*가 아니다. 그래도 명시 신호가 필요한 이유는 다르다 —
**보는 게임에서는 "지금 무슨 일이 일어나는 중인지"가 보여야 한다.** 물고 있다는 것과 언제 올라오는지가
읽혀야 화면을 계속 볼 이유가 생기고, 탭으로 앞당기려는 사람에게는 타이밍 단서가 된다.

> **느낌표는 이제 불필요할 가능성이 높다.** 입력을 요구하지 않으므로 링만으로 충분한지 프로토타입에서 판정할 것.

**입질 신호 구성**

1. **남은 시간 링** — 찌 둘레에 줄어드는 원호. 잔량 35% 아래로 떨어지면 색이 바뀐다.
   *"물었다"와 "얼마 남았다"를 한 번에 전달하고, 어종별 윈도우 차이(참치 0.6s vs 연어 1.2s)가 눈으로 보인다*
2. **찌 함몰 + 진동** — 확 잠기고 좌우로 떨린다
3. **물고기 파닥임** — 파동 진폭 ×1.8 / 주파수 ×3.2
4. **느낌표** — 옵션. 링만으로 충분한지는 프로토타입에서 판정
5. **물보라 파문** — 입질 순간 링 1회 방출

### 5-5. 관심 큐 가독성 — MVP 최우선 리스크 ★

관심 상태는 아이콘 없이 **행동으로만** 읽혀야 한다. 신호를 겹쳐 쓴다.

| 신호 | Roam | Interested |
|---|---|---|
| 발견 순간 | — | **멈칫 → 방향 전환 (§5-1)** |
| 속도 | 기준 | **2배 이상** |
| 진행 각도 | 사인파로 계속 흔들림 | **고정, 완전 직선** |
| 꼬리 비트 | 기준 | **주파수 ×1.8, 진폭 ×1.3** |
| 뱅킹 | 선회마다 기울어짐 | **없음** |
| 물살 트레일 | 없음 | **있음** |

**흔들림이 멈추는 것 자체가 신호다.** 다른 놈들이 다 꼬물거리는데 한 마리만 뻣뻣하게 직진하면 눈에 띈다. 폴백으로 하나씩 추가하는 게 아니라 **처음부터 전부 켠다.**

**탑다운이 이 리스크를 크게 줄여준다.** 측면 뷰였다면 물고기가 좌우로만 향해서 "찌 쪽으로 온다"를 방향으로 표현할 수 없었다. dorsal view에서는 **머리를 문자 그대로 찌 쪽으로 겨눌 수 있어서**, 사방에서 한 점으로 모이는 그림이 된다. 배경 물고기를 제각각 다른 방향으로 흩어놓는 것이 대비의 핵심.

**정지 이미지로는 검증할 수 없다.** 신호가 자세가 아니라 움직임이라 한 프레임에 담기지 않는다. 반드시 움직이는 빌드로 판정할 것 — 이 목적의 웹 프로토타입이 별도로 있다(입질 벤치).

**그래도 안 읽히면**: Roam 곡선을 더 구불구불하게 해서 대비를 키운다. 찌 주변 관심 반경 링은 최후의 수단 — UI 티가 난다.

### 5-6. 접근 방식은 조립한다 (v0.4 신설)

"목표가 생겼을 때 어떻게 다가가는가"는 한 덩어리가 아니라 **거리에 따라 넘어가는 단계**다.
보는 맛의 대부분이 여기서 나온다.

각 방식은 매 프레임 **(조준각 · 속도 · 반경 배수)** 만 돌려주고, 실제 이동은 공통 코드가 한다.
그래야 어떤 조합에서도 §5-3 의 선회 보장이 깨지지 않는다.

```
enter(f, sp, T)            단계 진입 시 1회
step(f, dt, sp, T, d)  →   { aim, speed, rBL }
```

| 방식 | 동작 | 연어 도달 |
|---|---|---|
| **직행** | 목표를 향해 최단으로 | 0.9초 |
| **돌진** | 빠르게 밀고 들어온다 | 0.8초 |
| **궤도 유지** | 하던 대로 헤엄치며 조금씩 밀려온다 | 0.5초 |
| **조심** | 다가오다 멈칫, 다시 다가온다 | 1.2초 |
| **선회 접근** | 옆으로 스쳐 지나갔다가 더 가깝게 다시 온다 | 1.8초 |
| **눈치보기** | 근처에서 서성이다 확 낚아챈다 | 2.2초 |

**어종별 조합**

```
연어    돌진
은빛 학공치  돌진
멸치    직행
노란 피라미  직행
오징어       조심 → (1.7유닛) → 눈치보기
청록 접시고기 선회 접근 → (1.0) → 직행
참치    궤도 유지 → (4.5) → 선회 접근 → (1.5) → 눈치보기
```

> **선회 접근은 원 궤도로 짜면 안 된다.** 반경을 시간으로 줄이면 각속도가 일정해서
> 궤도 도는 드론처럼 보인다. 실제 물고기는 미끼를 곧장 향하지 않고 **옆으로 스쳐 지나갔다가
> 돌아서 더 가깝게 다시 온다.** 그래서 '패스' 단위로 짠다 — 지나칠 때마다 이격거리가 절반이 되고,
> 지나친 직후엔 바로 안 꺾고 관성으로 흘렀다가 돌아서며, 55% 확률로 반대쪽으로 온다.

> ⚠️ **속도 배율의 하한.** 배율은 어종의 `approach` 에 곱해진다. 참치은 0.5(§1-3의 그 값)라
> 0.55배짜리 배율을 곱하면 접근이 20초를 넘고, *"잡을수록 참치이 멀어진다"* 가 아니라
> **"참치은 아예 안 잡힌다"** 가 된다. 원거리 배율은 **0.85 아래로 내리지 않는다.**

### 5-6-B. 물고기끼리도 피한다 (v0.5 신설) ★

지금까지 물고기는 서로를 **통과**했다. 궤도가 읽히는 건 의도지만, 서로 반응이
전혀 없으면 **각자 레일 위를 도는 장난감**으로 읽힌다. 바다처럼 보이려면
"저 무리가 앞을 막았으니 돌아간다"가 있어야 한다.

**단, 경로 함수를 건드리면 안 된다.** Lane·Loop 의 `p = f(t)` 순수성은 헤드리스
밸런스 검증과 결정론의 근거다(§4-1). 그래서 **놀람과 같은 오프셋**으로 얹는다.

```
회피벡터 = Σ (1 - d/R) · yieldK / d   ... 반경 R = 몸길이 × 3.6 안, **앞쪽만**
yieldK  = 상대몸길이 / (내몸길이 + 상대몸길이)      ← 우선순위
오프셋  += 회피벡터 / 내몸길이 · k · dt              ← 덩치가 클수록 덜 밀린다
오프셋  *= 0.16^dt                                   ← 감쇠
|오프셋| ≤ 몸길이 × 0.8                              ← 상한
```

| 규칙 | 왜 |
|---|---|
| **앞쪽만** 피한다 | 뒤에 있는 걸 피하지 않는다. 안 그러면 무리 뒤꽁무니가 서로를 밀어낸다 |
| 같은 무리끼리는 **안 피한다** | 대형(§4-4)이 회피와 싸워서 무리가 터진다 |
| 우선순위 = **상대 크기** | 멸치 떼가 참치를 만나면 멸치가 갈라진다. 그 반대가 아니다 |
| **합이 아니라 평균** | 합으로 두면 반경이 큰(=덩치 큰) 물고기가 이웃을 더 많이 보게 되어 **제일 많이 비키는 역설**이 생긴다. 실측에서 참치가 가장 크게 밀렸다 |
| 감쇠 + 상한 | §11-1 의 그 함정. 없으면 밀집 구간에서 궤도를 영구히 떠난다 |

실측(150초): 최대 이탈 멸치 0.50 · 연어 0.80 · 참치 **0.43** 유닛.
참치가 가장 덜 밀린다 — 우선순위가 의도대로 작동한다.

> ⚠️ **회피를 '적분 + 감쇠'로 만들면 드드득거린다 (v0.6에서 고침).**
> 피하면 멀어지고 → 감지가 끊기고 → 감쇠로 되돌아오고 → 다시 감지되는
> **극한 순환**이 생긴다. 게다가 오프셋은 *위치*를 옮기는데 머리 방향은
> **위치 차분**에서 나오므로, 작은 위치 떨림이 큰 방향 떨림으로 **증폭**된다.
>
> 실측: 각가속도 **16~18배**, 만새기 선회 반전 1회 → **512회**.
>
> → 적분하지 말고 **목표를 향한 2단 저역통과**(τ≈0.9s + 1.1s)로. 넘어갈 수가 없다.
> 고친 뒤 각가속도가 회피를 **끈 것과 같아졌다**(9 vs 10).

> ⚠️ **같은 종이 겹치는 진짜 원인은 회피가 아니라 스폰이었다.**
> `Loop.init` 이 중심을 **연못 한가운데(W/2 ± 1.2)** 에 몰아놨다. 같은 종이 둘이면
> 거의 같은 8자를 돌아 계속 겹친다 — 실측 겹침 **52%**. **회피로는 못 푼다**:
> 같은 궤도에 갇혀 있으면 밀어내도 다시 만나기 때문이다.
> → 중심을 연못 전체에 흩고, 같은 종끼리 **위상을 반대편으로** 민다.
>
> 무리 대형도 같은 종류의 버그였다. 랜덤 극좌표(`r = rnd(0.22, school.r)`)로 놓으면
> 두 마리가 같은 자리에 놓이는 걸 막을 방법이 없다 — 실측 겹침 **60%**.
> → **어긋난 쐐기(V) 대형**. 최소 간격이 구조적으로 보장된다. 겹침 **2% 이하**.

### 5-6-C. 같은 리듬을 반복하지 않는다 (v0.5 신설)

Hover-Dash 의 파라미터를 랜덤으로 줘도 **'부유-돌진-부유-돌진'이라는 리듬 자체**는
그대로 읽힌다. 파라미터가 아니라 **기분(mood)** 을 바꿔야 한다.

| 기분 | 확률 | 부유 시간 | 돌진 거리 | 연속 횟수 |
|---|---|---|---|---|
| `still` | 30% | ×2.4 | ×0.40 | 1~2 |
| `cruise` | 42% | ×1.0 | ×1.00 | 2~3 |
| `skittish` | 28% | ×0.26 | ×0.62 | 3~6 |

실측 부유 시간: 0.45 · 0.63 · 1.57 · 2.47 · 2.97 · **5.02** · **7.40** 초.
**편차 18.2배**(이전 2.1배). 세 가지 리듬이 눈으로 구분된다.

### 5-7. 입질이 성립한 뒤, 나머지 물고기 (v0.4 신설) ★

한 마리가 물었을 때 **주변 물고기가 언제 어떻게 반응하는가.**
이 게임에서 탭은 선택이므로(§1-1), *"탭하면 뭐가 좋은가"* 를 플레이어에게
알려줄 통로가 사실상 이것 하나뿐이다. UI 로 알려주면 안 된다 — **연못을 보고 알아야 한다.**

**두 사건을 분리한다.**

| 시점 | 반응 | 왜 |
|---|---|---|
| **① 물린 순간** | **주목**만. `noticeR` 안의 물고기가 0.35초 머리를 그쪽으로 튼다. **경로 이탈 없음** | 작은 소란이다. 여기서 흩어지면 탭 여부와 무관하게 똑같이 흩어져서 **정보가 0 이 된다** |
| **② 채는 순간**(회수 시작 — 탭이든 자동이든) | **놀람**. 실제로 흩어진다 | 물고기가 물 밖으로 끌려나가는 게 진짜 소란이다 |

**놀람 세기는 물린 채로 얼마나 놔뒀는지에 비례한다.**

```
scatter = StartleImpulse × (0.45 + 0.55 × clamp01(hookedTime / AutoReelDelay))
```

- 즉시 탭 → **45%**
- 자동 회수까지 기다림 → **100%**

이 한 줄이 게임의 핵심 규칙을 만든다.

> **빨리 채면 주변이 안 흩어진다. 늦게 채면 흩어진다.**

수치도 팝업도 없이 **보면 안다.** 그리고 이건 단순한 DPS 체크가 아니라 진짜 선택이 된다 —
참치이 접근 중이면 **작은 놈을 일부러 안 채는 게 이득**일 수 있다. 규칙 하나에서 딜레마가 나온다.

**흩어짐은 반드시 국소적이어야 한다.**

| 그때 그 물고기의 상태 | 반응 |
|---|---|
| 찌 근처에서 접근 중이었다(`hesitate`·`spiral` 막바지) | 가장 크게 흩어진다. 바로 옆에 있었으니까 |
| 관심은 있었지만 멀었다(`drift`·`wary`) | **안 흩어진다.** 목표가 사라졌으니 그냥 경로로 복귀 |
| 관심 없었다 | 아무 일도 없다 |

> ⚠️ **연못 전체를 흩으면 게임이 끊긴다.** 잡을 때마다 전체가 흩어지면
> `잡는다 → 5초 아무것도 없음 → 돌아오길 기다린다 → 잡는다` 가 된다.
> 이건 **"멍하니 보기만 해도 재밌다"의 정반대**다. 반경 밖은 반드시 무반응이어야 한다.

**놀람의 모양 — C-스타트.** 놀란 물고기는 *빨라지는 게* 아니라 **몸을 C 로 접었다 펴며
튕겨나간다.** 속도만 올리면 화면이 "재생 속도를 올린 것"으로 읽히고, 이 게임에서 그건
치명적이다 — **보는 맛이 목표**인데 놀람이 가장 눈에 띄는 순간이기 때문이다.
접히는 전반부는 거의 안 나가고 펴지는 후반부에 튕겨나간다(실측 1.2 → 4.5, 3.7배).
아트가이드 §2-6-B.

**선택 사항 — 물린 물고기 자체를 소란원으로 둔다.** 물린 채 버둥거리는 동안 찌 위치를
움직이는 놀람 발생원으로 취급하면, 위 공식 없이도 "오래 놔두면 주변이 흩어진다"가
**저절로** 나온다. 공식보다 이쪽이 보기에 낫지만 튜닝이 어렵다. 공식부터 넣고 비교할 것.

## 6. 연출

> 스파인 · 2D Bone · 프레임 애니메이션은 **전부 불필요**하다.
> AI로 스프라이트를 뽑는 파이프라인에서 리깅은 오답 — 리소스가 바뀔 때마다 다시 해야 한다.

### 6-1. 파동 셰이더 (전 어종 공용 1개) ★ 구현 방식 주의

> **⚠️ "서브디비전 쿼드에 정점 변위"는 SpriteRenderer로는 안 된다.**
> Unity의 Sprite는 Mesh Type이 Full Rect면 **정점이 4개(삼각형 2장)** 뿐이다.
> Tight로 바꿔도 알파 외곽을 따라간 불규칙 폴리곤이라 매끄러운 파동에 못 쓴다.
> 정점이 없으니 정점 변위로는 아무 일도 일어나지 않는다.

**세 가지 길과 선택**

| 방식 | 성립 | 비용 |
|---|---|---|
| **(A) UV 왜곡 (프래그먼트)** ← **추천** | SpriteRenderer 그대로 | 스프라이트에 여백 필요 |
| (B) Quad MeshRenderer + 커스텀 서브디비전 메시 | 정점 변위 가능 | 스프라이트 정렬·배칭 편의를 잃음 |
| (C) Unity 2D Animation Sprite Skinning | 가능 | **리깅** — 우리가 피하려던 바로 그것 |

**(A) UV 왜곡으로 간다.** 정점을 옮기는 대신 **텍스처를 샘플할 UV를 밀어준다.**
삼각형 2장으로도 되고, SpriteRenderer·Sorting·배칭을 그대로 쓴다.

```hlsl
// u = 머리(0) → 꼬리(1).  스프라이트는 머리가 오른쪽이므로 u = 1 - uv.x
float u     = 1.0 - i.uv.x;
float phase = _Time.y * _Freq + dot(worldPos.xy, _SeedVec);   // 개체별 위상 (§6-1 트릭)
float wave  = _Amp * u * u * sin(phase - u * 2.4);
float2 uv   = i.uv + float2(0, wave);
```

**대가가 하나 있다 — 몸이 스프라이트 사각형 밖으로는 못 나간다.**
UV를 밀면 샘플 좌표가 [0,1] 밖으로 나가고, 거기엔 그릴 게 없다.
→ **스프라이트 위아래에 몸통 높이의 30% 이상 투명 여백**을 확보해야 꼬리가 잘리지 않는다.
아트 가이드의 "여백 규격 통일"이 여기서 실제 의미를 갖는다. (아트 가이드 §3에 반영)

**이건 프로토타입으로 검증되지 않은 유일한 부분이다.** 웹 프로토타입은 폴리곤을 직접 그려서
정점 변위와 같은 결과를 냈지만, Unity에서는 위 방식이 다르다.
**구현 순서에서 이걸 최우선으로 확인할 것.**

---

- 로컬 X(머리→꼬리)를 따라 sin파로 UV 오프셋
- 진폭은 꼬리로 갈수록 증가: `amp * pow(u, 2)` (u = 머리 0 → 꼬리 1)
- **개체별 위상차 (배칭 유지 트릭)**: per-instance 데이터 대신 **월드 좌표를 위상 시드로** 사용
  `phase = _Time.y * freq + dot(worldPos.xy, seedVec)`
  → 물고기마다 위치가 다르니 자동으로 박자가 다르다. 추가 데이터 0, 드로우콜 증가 없음
- `_Speed`로 진폭/주파수 스케일 → 대시할 때 꼬리가 세게 친다

**탑다운에서 이게 물리적으로 정확하다** — 위에서 본 물고기가 좌우로 몸을 흔드는 건 실제 유영 동작이다.

### 6-2. 어종별 파동 파라미터 (같은 셰이더, 다른 성격)

| 어종 | 진폭 | 주파수 | 근거 |
|---|---|---|---|
| 연어 | 1.0 (기준) | 1.0 | 평범 |
| 멸치 | 0.6 | **1.8** | 작은 물고기는 잘게 빠르게 떤다 |
| 오징어 | **0.32** | 0.9 | 몸통이 뻣뻣. 외투막이 뻣뻣하다 — 흔들리는 건 다리다. 습성(정지→돌진)과도 일치 |
| 참치 | 1.4 | **0.7** | 크고 느긋하게 |

파라미터 4개만으로 4종의 성격이 갈린다.

### 6-3. 회전과 선회

**회전 (전 어종)** — 머리를 오른쪽(+X)으로 그렸으므로 각도를 그대로 넣으면 된다.
단, **각도를 목표로 보간(SmoothDamp)하지 말고 선회율로 깎아 돌린다** (§5-3):

```csharp
float target = Mathf.Atan2(toTarget.y, toTarget.x) * Mathf.Rad2Deg;
float delta  = Mathf.DeltaAngle(angle, target);
angle += Mathf.Clamp(delta, -turnRate * dt, turnRate * dt);
transform.rotation = Quaternion.Euler(0f, 0f, angle);
transform.position += (Vector3)(new Vector2(Mathf.Cos(angle*Mathf.Deg2Rad),
                                            Mathf.Sin(angle*Mathf.Deg2Rad)) * speed * dt);
```

보간과 선회율 제한은 결과가 완전히 다르다. 보간은 **남은 각도에 비례**해 돌아서 멈춰 있어도 제자리에서 돌지만,
선회율 제한은 **시간당 상한**이라 돌면서 반드시 앞으로 나아간다.
dorsal view라 좌우 반전 처리·각도 제한·뒤집힘 예외는 전부 불필요하다.

**선회 (참치만)** — 꼬리를 별도 스프라이트로 분리하고 **몸통 회전을 지연시켜 따라오게** 한다.

```
꼬리 각도 = 몸통 각도를 0.15초 지연시킨 값 + 유영 사인파
```

선회할 때 꼬리가 뒤에서 휙 끌려오고, 사인파가 유영 동작을 겸한다. 셰이더 없이 트랜스폼만으로 된다.

**왜 참치만인가**: 8자 궤도를 도는 참치은 항상 선회 중이라 효과가 크다. 직선 레인의 연어는 거의 안 돌고, 오징어는 제자리에 있다. 비용 대비 효과가 나는 건 참치뿐이다.

### 6-4. 그림자 — 탑다운에서는 필수

없으면 물고기가 수면 위에 붙은 스티커처럼 보인다.

- 물고기 아래에 흐릿한 타원 스프라이트를 **약간 오프셋**해서 배치
- **오프셋 거리와 흐림 정도로 깊이를 표현** — 깊은 물고기는 그림자가 멀고 흐리게, 얕은 물고기는 가깝고 진하게
- §4-3의 구역(상단=얕음 / 하단=깊음)과 연동하면 조작 추가 없이 깊이감이 생긴다

### 6-5. 획득 연출 — 이 게임의 유일한 보상 프레임 ★

조작이 거의 없는 게임에서 **잡히는 순간이 유일한 결과 표시**다. 그냥 사라지면 보상이 없다.
3단계로 나눈다.

| # | 구간 | 연출 |
|---|---|---|
| 1 | **끌어올림** 0.30s | 물고기가 수면 위로 솟는다. 스케일 ×1.2, **방사형 물보라**, 파문 링 1회 |
| 2 | **비행** 0.55s | 바구니로 포물선. 스케일 ×0.34까지 축소, 완만한 회전, 끝에서 페이드 |
| 3 | **입고** | 바구니 칸이 번쩍이고 **숫자가 튀며 증가** |

**탑다운에서 "위로 올라간다"를 어떻게 보여주나** — §6-4의 그림자를 그대로 쓴다.
물고기는 위로 올라가고 **그림자는 수면에 남으므로, 둘 사이가 벌어지면 그게 곧 높이다.**
스케일 확대와 그림자 분리 두 가지만으로 물 밖으로 나오는 게 읽힌다. 별도 리소스가 필요 없다.

**집계는 도착 순간에 올린다.** 잡자마자 숫자를 올리면 비행이 장식이 되어버린다.
0.85초 늦게 오르는 대신 **비행이 결과를 실어 나르는 것**이 되고, 그게 보상의 리듬을 만든다.

> **구현 주의**: 헤엄치는 물고기와 날아가는 물고기는 **같은 렌더 함수**를 써야 한다.
> 따로 두면 한쪽에만 눈이나 무늬가 빠져서 물고기로 안 읽히는 사고가 난다 (실제로 겪음).

## 8. 데이터 모델

> 점수 · 도감 · 납품 · 강화가 전부 붙을 예정이므로 **세션 결과를 점수로 저장하면 안 된다.**

### 8-1. 나쁜 설계로 갔을 때 3개월 뒤

```
세이브:  { totalScore: 1250 }
```

납품 시스템 추가 → *"참치 3마리를 납품하세요"* → **플레이어가 참치을 몇 마리 갖고 있는지 알 수가 없다.**
1250점에서 역산 불가 → 유저 데이터를 밀거나 복잡한 마이그레이션.

### 8-2. 저장 원본

```csharp
[Serializable]
public struct CatchRecord {
    public int   speciesId;
    public float sizeCm;        // MVP 미표시, 값은 굴린다
    public long  caughtAtUtc;
    public int   spotId;
}

public class PlayerData {
    public Dictionary<int, int>        inventory;  // speciesId → 수량  ← 납품·강화 소모원
    public Dictionary<int, CodexEntry> codex;      // 최초획득 / 최대사이즈 / 누적획득
    public int bestSessionScore;
}
```

### 8-3. 파생 계산 (저장하지 않음)

| 값 | 계산식 |
|---|---|
| 세션 점수 | `Σ (species.baseScore × SizeMultiplier(sizeCm))` |
| 도감 진행도 | `codex` 순회 |
| 납품 가능 여부 | `inventory` 조회 *(후속)* |
| 강화 재료 환산 | `inventory` × 환산표 *(후속)* |

> **원칙: 인벤토리로 점수를 계산할 수 있지만, 점수로 인벤토리를 계산할 수는 없다. 정보가 더 많은 쪽을 저장한다.**

MVP에서는 `inventory`를 쌓기만 하고 소모처가 없다. 그래도 지금부터 쌓는다.

### 8-4. 연어 가치 밸런싱 — 리셋 동기 보호 ★

물고기가 소모 자원이 되는 순간 **"어차피 다 재료인데 아무거나 많이 잡는 게 이득 아닌가"** 가 성립해버리고, §2-3의 의사결정이 죽는다.

해결은 소모처를 희귀도별로 나누는 게 아니라 **환산값을 점수와 같은 비율로 유지하는 것**:

```
연어 1 · 멸치 2 · 오징어 5 · 참치 30   ← 점수도, 재료 환산값도 동일 비율
```

참치 배점이 30인 이유: 노림 플레이는 연어·멸치를 통째로 버리므로, **참치 한 마리가 세션을 만들 만큼** 무거워야 기대값이 역전된다. 15로는 노림 플레이가 느긋한 플레이보다 점수가 낮았다(프로토타입 실측).

그리고 **참치 1마리 잡는 시간 < 연어 15마리 잡는 시간**이 되게 튜닝한다.

**결과 — 분산이 큰 구조**

**프로토타입 실측** (90초, 봇, 세션 18회 평균)

| | 마릿수 | 점수 | 폭 | 참치 |
|---|---|---|---|---|
| 완전 무입력 방치 | 10.9 | 40.9 | 8~93 | **0.8** |
| 자동 + 즉시 탭 | 12.9 | 40.5 | 18~88 | 0.6 |
| **선별** (연어·멸치 놓아줌) | 1.9 | 36.7 | 0~70 | **1.1** |

- **무입력만으로 40점** → 방치가 실제로 성립한다 ✅
- 탭은 **양↑ 질↓** → 이득도 손해도 아닌 취향 ✅
- 선별 해금은 **참치 2배** → 불편 제거가 아니라 새 능력 ✅
- 세 방식 모두 폭이 크다(0~93) → **자리 선택이 지배적 변수** ✅

**찌 위치만 바꿔본 결과** (무입력, 위치별 12세션)

| 자리 | 점수 | 참치 |
|---|---|---|
| (13, 2) | **19.3** | 0.2 |
| (3, 4.5) | 39.9 | 0.8 |
| (8, 4.5) | 39.8 | 0.5 |
| (8, 7) | **46.4** | 0.9 |

**손 하나 안 대고 자리만 바꿔도 점수가 2.4배 갈린다.**
마릿수는 거의 같은데 *무엇이 잡히느냐*가 달라진다 — 배치 중심 설계의 근거다.

## 8-5. 성장 축과 과금

> **원칙: 불편을 팔지 않는다.**
> "멍하니 봐도 재밌다"가 이 게임이 내세우는 것이라면, 그걸 유료로 열어주는 순간
> 무료 버전은 **광고와 다른 물건**이 된다. 자동 회수는 처음부터 기본이다.

| 단계 | 해금 | 무엇이 달라지나 |
|---|---|---|
| **기본** | 자동 회수 | 손 안 대도 돌아간다. 조작은 찌 배치뿐 |
| 1 | **선별 회수** ★ | 어종별 놓아주기. **"이제 참치을 노릴 수 있다"** — 가장 큰 전환점 |
| 2 | 세션 시간 증가 | 한 자리에 더 오래 머문다 |
| 3 | 낚시터 추가 | 어종 구성이 다른 물 |
| 4 | 찌 개수 | 동시에 두 자리 |
| 5 | 자동 재배치 | 좋은 자리를 알아서 찾는다 (진짜 완전 방치) |
| 후속 | 오프라인 수급 | 껐다 켜도 쌓여 있다 |

**선별 회수를 1번에 두는 이유**: 실측상 이것만으로 참치 획득이 2배가 된다(0.7 → 1.5).
불편을 없애는 게 아니라 **플레이 방식 자체가 바뀌는 능력**이라, 유료화해도 정당하고
"돈 냈더니 게임이 재밌어졌다"가 아니라 **"돈 냈더니 다른 게임이 열렸다"** 가 된다.

**절대 유료로 하면 안 되는 것**: 자동 회수. 이건 게임의 기본 상태다.

- **평균이 높으니** 노림 플레이가 잘하는 플레이다 → 실력 보상
- **망할 수 있으니** 느긋한 플레이도 유효하다 → 방치 보상
- **참치을 잡으면 짜릿하다** → 매번 나오면 감흥이 없다

노림 플레이가 *항상* 30점이면 정답이 하나로 굳고 게임이 지루해진다. **분산이 있어야 두 스타일이 공존한다.**

- 놀람 → **발견 동작** → 관심 큐 → 히트 → **자동 회수**(큰 소란)
- **선별 회수** — 어종별 놓아주기(작은 소란). MVP에 넣되 해금 연출은 후속
- 탭 = 즉시 회수 (선택 조작)
- 입질 신호: 남은 시간 링 + 찌 함몰 + 파닥임
- 우측 바구니 집계, 세션 타이머, 결과 화면
- 인벤토리 · 도감 데이터 적립 (도감만 UI 노출)
- 파동 셰이더 + 회전 스무딩 + 그림자 + 수면 왜곡
- 참치 꼬리 분리 + lag

**제외 (후속)**

- 납품 / 강화 / 미끼 / 장비 / 시간대·날씨 / 자동낚시 / 재화 / 어종 확장 / 사이즈 UI

**검증 목표 — 이거 안 되면 갈아엎는다**

1. 궤도를 보고 **미리** 찌를 놓는 행동이 실제로 나오는가?
2. **손을 놓고 봐도 재밌는가?** 무입력 90초가 지루하지 않은가 *(이 방향의 진짜 관문)*
3. **"저기가 아니라 여기였구나"** 하고 찌를 옮기고 싶어지는가?

### 11-0. 이 값들은 '확정'이 아니라 '실기에서 정한다' (v0.4)

위 수치는 **벤치 실측 기준값**이지 확정값이 아니다. 실측했다는 것과 확정됐다는 건 다르다.
느낌 값은 실제 화면(폰, 90초 세션, 찌를 던지고 잡는 흐름) 안에서만 판단된다.

> ⚠️ **`FishingTuning.cs` 가 `public const` 인 것은 버그다.**
> C# 의 `const` 는 컴파일 시점에 호출부로 박히는 값이라 런타임에 못 바꾼다.
> 숫자 하나 고치려면 **재컴파일 → 플레이 모드 종료** — 세션을 처음부터 다시 돌려야 한다.
> "게임하면서 수정"이 구조적으로 막혀 있다.
>
> **ScriptableObject 로 바꿀 것.** SO 는 애셋이라 **플레이 모드 중에 고친 값이 종료 후에도 남는다.**
> `[Range]` 를 달면 인스펙터에서 슬라이더가 되고 즉시 반영된다.
> 빌드에서도 만지려면 오버레이 + **현재 값을 JSON 으로 뱉는 버튼**이 필요하다(빌드→애셋은 수동 반영).

**단, 두 덩어리로 갈라야 한다.**

| | 무엇 | 인스펙터 |
|---|---|---|
| **느낌** | 머리 추종·슬립 상한, 사행 폭·주기, 최소 선회 반경, 파동 진폭·박자, 뱅킹, 꼬리 지연 | 자유롭게 |
| **⚠️ 규칙** | 참치 접근 속도, `lureChance = 0`, 오프셋 상한, 재착수 반경 배율, 근접 선회 보정 | **경고색 + 이유 병기** |

전부 슬라이더로 만들면 참치 `approachSpeed 0.5` 는 누군가 반드시 올린다. 너무 느려 보이니까.
그리고 그 순간 §1-3 이 죽는다. `CLAUDE.md` 의 "절대 바꾸지 말 것" 표를 **인스펙터 안에** 띄우는 셈이다.

**튜닝 우선순위**: 목표 성과가 안 나오면 **호기심 확률을 먼저 건드린다.** 접근 속도나 입질 윈도우는 체감(긴장감)을 직접 바꾸므로 마지막에 손댄다.

**밸런스는 정지 상태로 검증할 수 없다.** 위 수치는 전부 프로토타입(입질 벤치)에서 세션을 20회씩 돌려 얻은 실측값이다. 종이 위에서 계산한 v0.2의 목표치(느긋 15점 / 노림 2~33점)는 실제와 크게 달랐다 — **호기심 확률이 개체당인데 개체 수를 안 넣고 계산했기 때문**이다.

### 11-1. 구현 시 밟은 함정 (유니티 이식할 때 그대로 반복하지 말 것)

| 함정 | 증상 | 원인 |
|---|---|---|
| 스폰 시 경로 파라미터 t를 랜덤하게 줌 | 물고기가 화면 밖에 생성 | `pos = origin + dir·speed·t` 라서 t=20이면 이미 24유닛 진행한 위치 |
| 랩 처리에서 경로 원점에 폭을 **누적 가산** | 한 프레임에 여러 번 발동해 물고기가 날아감 | 위치는 다음 프레임에야 갱신되므로 조건이 계속 참 → **목표 좌표를 직접 지정할 것** |
| 무리 추종 개체의 궤도 복귀 오프셋 | 20유닛짜리 오프셋 → 순간이동 | 추종 개체는 자기 경로를 안 쓰는데 그걸 기준으로 오프셋을 계산 |
| 놀람 임펄스에 누적 상한 없음 | 연속 재착수 시 물고기가 화면 밖으로 | `offset +=` 만 하고 상한이 없음 |
| 연속 재착수 페널티가 **반경**을 2.5배 | 참치 놀람 반경이 7.5유닛(연못 폭의 절반) | 페널티는 **지속시간**이 받고 반경은 1.35배까지만 |
| **위치와 회전을 따로 굴림** | 속도가 0에 가까운 순간 **제자리에서 빙글** 돈다 | 각도를 목표로 보간하지 말고 **선회율 제한 + 머리 방향 전진** (§5-3) |
| 돌진 순간에 방향 결정 (오징어) | 최대 180°를 즉시 돌아야 해서 제자리 회전 | 부유 중 미리 조준해두고 향한 쪽으로만 돌진 |
| **선회율을 직접 지정** | 느린 어종이 제자리에서 돈다 (반경 몸길이의 3.5%) | **ω = v / R_min** 으로 뒤집을 것 (§5-3) |
| **최소 선회 반경 > 도착 판정** | 물고기가 목표 주위를 영원히 맴돈다 | 근접 보정(§11) + **속도 적합**. 선회율을 올리면 팽이가 된다 |
| **메시의 앞 방향이 -X** | 꼬리가 앞장서서 헤엄친다 | `rotation.z = heading` 은 +X 를 진행 방향에 맞춘다. 정지 이미지로는 안 보인다 |
| **그림자를 3D 복제본으로** | 그림자의 지느러미가 몸통을 뚫고 올라와 구멍처럼 보인다 | z 를 눌러 **수면에 눕힐 것**. 물고기는 그 평면 위로 띄운다 |
| **선회율·속도를 평활화 없이 꼬리에 연결** | 꼬리가 매 프레임 튀어 '퍽퍽' 끊긴다 | 둘 다 프레임 차분이라 그 자체로 떨린다. 저역통과 필수 (변화 RMS 0.027 → 0.007) |
| **화면 밖 랩에서 속도 상한 없음** | 랩하는 순간 꼬리가 최고 박자로 한 번 튄다 | 좌표 순간이동이라 v 가 1000까지 계산된다. 상한을 둘 것 |
| **꼬리 정점의 `u` 를 1 이상으로 늘리고 진폭을 그대로** | 꼬리가 몸길이의 35%씩 휘둘러 바나나가 된다 | `WAVE_K` 로 환산할 것 — §6-1 에서 이미 밟은 함정을 3D에서 또 밟았다 |
| **지느러미 밑동이 점 하나** | 붙어 있는데 **떨어져 보인다** | 몸통에서 나오는 부분이 서브픽셀로 얇아진다. 밑동을 선분으로 둘 것 |
| 그 반동으로 **지느러미를 키움** | 이번엔 지느러미가 여러 개로 보인다 | 꼬리와 실루엣이 경쟁한다. **꼬리가 유일한 큰 요소** — 가슴은 꼬리의 절반 이하 |
| **눈 원반을 표면 법선에 맞춰 세움** | 위에서 보면 눈이 초승달로 잘린다 | 탑다운이므로 원반을 눕히고 국소 최고점 위에 올린다 |
| **접근 방식의 속도 배율에 하한이 없음** | 참치 접근이 20초를 넘어 아예 안 잡힌다 | 배율은 어종 `approach` 에 곱해진다. 원거리 하한 0.85 (§5-6) |

공통 교훈 둘:
- **경로 기반 이동에서는 오프셋과 원점에 반드시 상한과 안전망을 둔다.**
- **이동과 회전은 한 몸이다.** 따로 굴리는 순간 몸이 옆으로 미끄러지거나 제자리에서 돈다.
- **선회는 각속도가 아니라 반경으로 생각한다.** 각속도를 직접 주면 느린 놈은 팽이가 되고,
  빠른 놈은 소용돌이를 돈다. 반경을 정하고 거기서 각속도를 뽑으면 둘 다 사라진다.
- **정지 화면으로 안 잡히는 버그가 따로 있다.** 앞뒤가 뒤집힌 메시, 게걸음, 꼬리 떨림,
  제자리 회전 — 전부 렌더 한 장으로는 정상으로 보인다. **움직여서 재야 한다.**

### 12-2. 만드는 순서 — 수직 슬라이스로

> **원칙: 재미가 걸린 것부터, 위험한 것부터.** 껍데기(UI·세이브·씬 전환)는 마지막이다.

| 단계 | 내용 | 끝나면 확인할 것 |
|---|---|---|
| **1** | 수면 사각형 + `PathEvaluator` + `Fish` 4종 (**플레이스홀더 도형으로**) | 4종의 궤도가 각각 구분되어 보이는가 |
| **2** | **파동 셰이더 (§6-1 UV 왜곡)** ← **여기를 미루지 말 것** | 꼬리가 안 잘리는가. 개체마다 박자가 다른가 |
| **3** | `Bobber` + 상태머신 + 자동 회수 + 유인 | 손 놓고 90초가 지루하지 않은가 |
| **4** | 획득 연출 (§6-5) + 그림자 + 수면 왜곡 | 잡히는 순간이 기분 좋은가 |
| **5** | 실제 스프라이트 교체 | 가로 100px에서 4종이 구분되는가 |
| **6** | 사운드 | 소리를 끄면 확 심심해지는가 (그래야 정상) |
| **7** | 세션·결과·집계 UI, 세이브 | — |
| **8** | 낚시터 2곳 + 이동, 도감 | — |

**2단계를 2번에 둔 이유**: 이 프로젝트에서 **유일하게 프로토타입으로 검증 안 된 부분**이다.
웹 프로토타입은 폴리곤을 직접 그려 정점 변위와 같은 결과를 냈지만 Unity에서는 방식이 다르다.
UV 왜곡이 기대만큼 안 나오면 아트 규격(여백)까지 되돌아가야 하므로, **2일차에 알아야지 3주차에 알면 안 된다.**

**1단계를 플레이스홀더로 하는 이유**: 아트가 없어도 궤도·상태머신·밸런스는 전부 검증된다.
실제로 이 프로토타입 전체가 도형만으로 만들어졌고, 그걸로 밸런스 오류 두 건과 이동 버그 네 건을 잡았다.
**아트를 기다리느라 코어를 못 만드는 상황을 만들지 말 것.**

### 12-3. 웹 프로토타입에서 그대로 가져올 수 있는 것

`bite-bench.html`은 로직 참고용으로 남겨둔다. 아래는 거의 1:1로 옮겨진다.

- `PathEvaluator` — 4가지 궤도 수식. 순수 함수라 그대로
- `steer` / `advance` — 선회율 제한 전진 (§5-3)
- 상태머신 전이 조건과 타이머
- `startle` / `lure` 의 거리 판정과 상한 처리
- §7의 모든 수치

**옮길 때 주의**: 웹은 `update(dt)`를 직접 호출하지만 Unity는 `Update()`의 `Time.deltaTime`이다.
전부 dt 기반이라 그대로 동작하지만, **프레임 드랍 시 dt가 튀는 것만 클램프**할 것 (`Mathf.Min(dt, 0.05f)`).
